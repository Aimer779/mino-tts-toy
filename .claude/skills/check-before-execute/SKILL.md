# Check Before Execute: 执行前 Checkpoint

在修改代码前，做一次 checkpoint。说清楚你要做什么、怎么做、怎么验证。用户确认后，你再动手。

## 触发条件

- spec 确认后，准备开始写代码
- 用户说"先别改代码"、"checkpoint"、"确认一下"
- 任何即将修改代码前的时刻

## 标准流程

1. 输出 checkpoint（当前理解、目标、动作、风险、验证方式）
2. 等待用户确认
3. 用户确认后，开始执行

## 输出格式

```
## Checkpoint

### 当前理解
[用一句话描述当前任务]

### 核心目标
[本轮要收敛的具体问题]

### 下一步动作
1. 修改 [文件路径] 的 [函数/组件]
2. 新增 [文件路径] 的 [函数/组件]
3. 删除 [文件路径] 的 [无用代码]

### 风险
- 可能影响 [已有功能]
- 可能遇到 [技术难点]

### 验证方式
- 构建：[具体命令]
- 测试：[具体命令]
- 手动：[具体操作和预期现象]

等你确认后，我再执行。
```

## 规则

| 场景 | 做法 |
|------|------|
| 动作太模糊（"优化一下"） | 细化到具体文件和函数 |
| 没有风险识别 | 必须补充，不能写"没问题" |
| 验证方式是"检查一下" | 细化到具体命令和预期输出 |
| 用户说"直接做" | 视为批准，但仍要输出 checkpoint |

## 禁止

- 不要跳过 checkpoint 直接开始改代码
- 不要说"我理解了，直接开始吧"
- 不要把风险写成"没问题"
- 不要把验证方式写成"检查一下"

## 后续动作

checkpoint 确认通过后，模型开始执行代码。执行完成后，进入 `verify-by-evidence` 验证结果。
